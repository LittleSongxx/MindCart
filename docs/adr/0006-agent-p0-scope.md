# ADR-006：AI Agent 工程化 P0 范围（含「明确不做」清单）

日期：2026-09-16 ｜ 状态：已实施并实测

## 背景

基于 60+ 篇跨公司真实面经的题族频率分析（见 docs/interview-research 结论），
对 AI 域做针对性补强。原则：每个设计都要能说清「真实故障/需求是什么、面试问法是什么」；
说不清的不做——**不做的决策同样入档**。

## 做了（各条的真实依据）

| 项 | 真实问法依据（面经频率） |
|---|---|
| 混合检索 BM25+RRF（ADR-007） | 「为什么引入 BM25/两路怎么排序/举个混合优于单路的 case」H2，4+来源 |
| SSE 流式问答（ADR-008） | 「从用户输入到前端输出完整链路」H3，5 来源 |
| LLM 瞬时错误重试 + 参数解析显式终止 + 循环指纹检测 | 「工具超时是失败还是结果未知」「重复尝试/路径震荡怎么处理」H2 |
| token 采集入 agent_run | 「更换模型如何记录 Token 与价格口径」H2 |
| QA 多轮会话（最近3轮+字符预算） | 「上下文越来越长怎么办」「会话表字段设计」H3 |
| 注入对抗：提示词边界 + 评测注入题 | Prompt Injection L1-H1，高区分度 |
| 评测 v1 确定性断言（ADR-010） | 「评测集怎么构造/接近100%可信吗」H2 + 字节评测岗 JD 原文 |

## 明确不做（附理由与触发条件）

- **熔断器框架/降级链**：已有 `isFatalModelError` 致命错误早停覆盖「欠费/Key 失效」类；
  瞬时类由重试覆盖。半开探测等中间态在演示流量下无真实触发场景。
  触发条件：QPS 使重试放大故障时引入。
- **per-user 并发闸 / 检索缓存 / 上下文窗口管理**：上量才成立的优化。
  触发条件：任务量/延迟指标显示饥饿或超窗。
- **MCP Server**：工具目录 6 个、单应用私有调用；小目录全量注入更简单且少一个检索故障点
  （面经 AG-03 追问的标准答案）。能讲清 2026-07-28 版本语义即可。触发条件：出现多客户端共享工具需求。
- **多 Agent / Planner-Executor**：导购步骤可枚举+强校验，单 Agent+确定性状态机是正确形态。
- **LLM judge / Wilson CI / 密封 holdout**：n<50 时无解释力；等确定性指标跑稳、集子扩大再上。
- **Spring AI 2.0 升级**：2.0（2026-06 GA）要求 Boot 4.0；项目锁 Boot 3.5 是刻意选择，
  1.1.x 的工具循环自研（chatCompletion 裸 HTTP）反而使循环完全可控可观测。
